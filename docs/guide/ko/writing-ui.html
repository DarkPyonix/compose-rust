UI 작성하기

컴포저블, 상태, 이벤트

compose-rust의 작성 API는 Compose를 따릅니다. 컴포저블은 함수이고, 위젯은 Compose의 이름을 가진 호출이며, 상태는 remember 에 두고, 상태가 바뀌면 그것을 읽은 코드만 다시 실행됩니다. 무엇이 바뀌었는지 찾으려고 트리를 비교하는 일은 없습니다.

API가 있는 곳

작성 API는 develop 에 있고 2026-11-14의 compose-rust 1.0.0과 함께 릴리스됩니다 (#23, #64). crates.io의 0.0.1 크레이트에는 없습니다. 1.0.0 전까지는 시작하기에 나온 대로 이 저장소의 체크아웃에서 씁니다. 릴리스 전에 이름이 바뀔 수 있습니다.

컴포저블은 함수입니다

함수에 #[composable] 을 붙이고 그 안에서 위젯을 부릅니다. glob import 두 줄이면 전부 들어옵니다. 상태와 effect는 compose_rust::runtime 에서, 위젯과 Modifier 는 compose_rust::ui 에서 옵니다.

#[composable] 은 Compose 컴파일러 플러그인이 @Composable 함수에 하는 일을 합니다. 호출에 그룹을 주고, if 와 match 의 가지마다 따로 그룹을 주고, 함수를 건너뛸 수 있고 다시 시작할 수 있게 만듭니다. 그룹을 손으로 쓰는 일은 없습니다. 그룹은 continue, break, return, ?, 되감기를 지나도 맞게 닫힙니다. 그룹을 사용자가 아니라 매크로가 갖기 때문입니다.

launch 는 모든 선택을 기본값으로 두고 컴포저블을 애플리케이션으로 실행합니다. application 은 같은 함수를 Compose Desktop의 이름으로 부른 것입니다. 테마와 창을 정하는 법은 아래 실행 설정에 있습니다.

위젯은 문장 하나입니다

Text("Hello") 는 위젯의 기술(description)을 만듭니다. 문장이 끝나면 그것이 composition에 넘어갑니다. 그 사이의 메서드는 Compose가 이름 붙은 인자로 받는 것을 정합니다. Text(title).type_role(TypeRole::Title).max_lines(1) 은 Compose의 Text(title, style = ..., maxLines = 1) 입니다.

  • 위젯이 없으면 안 되는 것이 인자입니다. Text 는 글을, Button 은 레이블을, Slider 는 값을, Dialog 는 열려 있는지를 받습니다. 나머지는 모두 메서드입니다.
  • 자식은 클로저입니다. 컨테이너는 content 를 부를 때 자식을 구성하고, 클로저는 그 자리에서 바로 실행됩니다. Row().content(|| { ... }) 처럼 씁니다.
  • 모든 위젯이 Modifier 를 받습니다. Compose처럼 값 Modifier 에서 사슬을 시작합니다. Modifier.fill_max_width().padding_role(SpaceRole::Md) 처럼 씁니다. 수정자마다 노드의 사슬 안에 정해진 자리가 있으므로 부르는 순서는 상관없습니다.
  • 위젯을 변수에 묶지 않습니다. let 으로 묶은 위젯은 변수가 스코프를 벗어날 때 구성되므로, 형제들 사이의 엉뚱한 자리에 들어갑니다.

위젯 어휘는 스키마의 것이고, 위젯 레퍼런스에 있습니다. 작성 API는 자기 위젯이나 속성을 따로 정의하지 않으므로, 쓸 수 있는 것과 렌더러가 그릴 수 있는 것이 같은 목록입니다. minimal 샘플은 스키마의 모든 컨트롤을 모은 놀이터입니다.

직접 만드는 컴포저블

화면을 Compose에서처럼 함수로 나눕니다. 매개변수는 평범한 Rust 매개변수이고, 컴포저블이 자기 내용을 받을 때는 클로저 매개변수를 씁니다.

매개변수가 지난번과 같은 호출은 건너뜁니다. 다시 실행되는 스코프 안에서 제목과 상태가 같은 task_row 는 본문을 실행하지 않고, 그 노드도 그대로 남습니다. 무엇을 비교할 수 있는지는 매크로가 매개변수의 타입을 보고 정합니다. Clone 과 PartialEq 가 아닌 매개변수, 빌림, 제네릭, impl Trait 은 비교할 수 없으므로, 그런 것을 받는 함수는 건너뛰지 않고 매번 호출한 쪽이 다시 실행합니다.

상태와 recomposition

mutable_state_of(value) 는 MutableState 를 만듭니다. 상태는 자신을 읽은 스코프를 기록합니다. 상태에 쓰면 정확히 그 스코프들이 무효가 되고, 다음 프레임에 다시 실행됩니다. 바뀐 것을 찾는 방법은 이것이 전부입니다.

호출하는 일
state.get()값을 읽고, 지금 스코프를 그 상태에 구독시킵니다.
state.with(|value| ...)참조로 읽습니다. 목록처럼 복제하기에 큰 값에 씁니다.
state.get_untracked()구독하지 않고 읽습니다. 스코프가 아닌 핸들러 안에서 씁니다.
state.set(value)씁니다. 지금 값과 같은 값이면 아무것도 바뀌지 않습니다.
state.update(|value| ...)값을 그 자리에서 바꿉니다.
derived_state_of(|| ...)다른 상태에서 계산한 값입니다. 결과가 바뀔 때만 읽은 쪽이 다시 실행됩니다.
  • 상태는 핸들입니다. 복제하면 같은 값을 가리키는 두 번째 핸들이 생깁니다. move 클로저는 이렇게 상태를 가져갑니다. 먼저 복제하고, 복제본을 옮깁니다.
  • 같은 값을 쓰는 데는 비용이 없습니다. 기본 정책은 PartialEq 로 비교합니다. mutable_state_of_with_policy(value, never_equal_policy()) 는 모든 쓰기를 변화로 봅니다. 그 자리에서 바꾸는 긴 목록처럼 비교하기 비싼 값에 씁니다.
  • 한 프레임의 쓰기는 합쳐집니다. 다음 프레임 전에 여러 번 쓰면 recomposition은 한 번입니다.
  • 글 하나가 바뀌면 레코드 하나가 나갑니다. Text 하나를 바꾸면 속성 레코드 하나가 나가고, 형제와 부모는 실행되지 않습니다.

calculator 샘플은 표시창, 메모리 레지스터, 계산 기록을 상태에 둡니다. todo 샘플은 오천 행짜리 목록을 never_equal_policy 상태 하나에 둡니다.

위치 기반 기억과 키

remember(|| ...) 는 호출 자리가 처음 구성될 때 클로저를 실행하고, 그 뒤로는 매번 같은 값을 돌려줍니다. 값은 호출 자리, 곧 그룹 경로와 그 안의 호출 순서에 속합니다. 분기가 더 이상 타지 않으면 그 분기가 기억한 것도 함께 사라집니다. 반복이 짧아지면 잃은 회차의 값도 버려집니다. remember_with_key(key, || ...) 는 키가 바뀌면 값을 다시 계산합니다.

반복문에서는 순서가 맞는 정체성이 아닐 때가 있습니다. 항목이 움직일 수 있다면 각 항목을 key 로 감쌉니다. 키가 있는 항목이 자리를 바꾸면 지우고 다시 만드는 대신 이동으로 나가고, 그 항목이 기억한 값도 따라갑니다.

지연 목록도 같은 방식으로 items_keyed 를 통해 키를 받습니다. 목록과 스트리밍을 보세요.

effect

구성(compose)은 화면을 기술할 뿐 다른 일은 하지 않습니다. 런타임이 스코프를 실행할 수도, 건너뛸 수도, 다시 실행할 수도 있기 때문입니다. composition의 한 자리에 속하는 일은 effect에 둡니다. effect는 composition이 적용된 뒤, UI 스레드에서, 같은 Host 호출 안에서 실행됩니다.

함수Compose 이름실행되는 때
side_effect(|| ...)SideEffect자기 스코프의 composition이 적용될 때마다.
launched_effect(key, || async { ... })LaunchedEffect호출 자리가 들어올 때 시작하는 future입니다. 키가 바뀌면 다시 시작하고, 떠나면 취소됩니다.
disposable_effect(key, || { ...; on_dispose(|| ...) })DisposableEffect호출 자리가 들어오거나 키가 바뀔 때 실행됩니다. 정리 함수는 다음 실행 전과 떠날 때 실행됩니다.
remember_coroutine_scope()rememberCoroutineScope핸들러에서 future를 시작할 스코프입니다. 호출 자리가 떠나면 취소됩니다.

future는 런타임이 가진 작은 실행기가 UI 스레드에서 폴링합니다. 기다리는 데는 비용이 없고, future를 깨우는 쪽이 프레임을 요청합니다. delay 는 정한 시간만큼, with_frame_nanos 는 다음 프레임까지 기다립니다. recomposition 도중의 상태 쓰기는 다음 프레임으로 미뤄지므로, composition이 자기 자신을 먹이지 않습니다.

워커 스레드의 일

핸들러, composition, effect는 모두 UI 스레드에서 돌므로, 멈추는 일은 다른 곳에서 해야 합니다. PTY 읽기, 네트워크 호출, 파일 I/O가 그렇습니다. 나가는 길은 둘입니다.

  • with_worker(|| ...) 는 클로저를 워커 스레드에서 실행하고, 그 결과로 UI 스레드의 future를 이어 갑니다. Compose의 withContext(Dispatchers.IO) 입니다. let text = with_worker(move || std::fs::read_to_string(path)).await;
  • 직접 만든 스레드가 상태에 씁니다. MutableState 는 Send 입니다. 워커가 상태에 쓰면 변화가 큐에 들어가고 프레임이 요청되며, UI 스레드는 그 상태를 읽은 스코프만 다시 구성합니다.

어느 쪽이든 사용자 코드는 경계 함수를 부르지 않고, 두 쪽 사이에 차오를 큐도 없습니다. chat 샘플은 자기 스레드에서 답을 몇 글자씩 스트리밍합니다. notepad 와 todo 샘플은 UI 스레드 밖에서 파일을 읽고 저장합니다.

이벤트 핸들러

핸들러는 평범한 Rust 클로저이고, on_click, on_change, on_submit 같은 메서드로 줍니다. 핸들러는 'static 이어야 하므로 쓰는 것을 직접 가집니다. 상태를 복제하고, 복제본을 옮겨 넣습니다.

핸들러는 동기로 실행됩니다. 렌더러가 자기 UI 스레드에서 Host를 부르고, 핸들러가 실행되고, 런타임이 recomposition을 하고, 바뀐 것의 배치가 같은 호출로 돌아갑니다. 큐에 쌓이는 것은 없습니다. 핸들러가 UI 스레드를 잡고 있으므로 가벼워야 하고, 핸들러가 시작하는 일은 위처럼 워커로 보냅니다.

키 소비: Enter와 Shift+Enter

채팅 입력창은 Enter 로 보내고 Shift+Enter 로 줄을 바꿔야 합니다. on_submit 핸들러가 있는 여러 줄 TextField 가 정확히 그렇게 합니다. Enter 는 글을 제출하고 Shift+Enter 는 줄을 바꿉니다.

직접 정하려면 on_key_down 이 보조 키와 함께 키를 봅니다. 지금 스키마가 싣는 키는 Key::Enter 하나입니다. 이벤트에 consume() 을 부르면 입력창은 그 키에 반응하지 않습니다. 이 답은 같은 호출의 반환값으로 렌더러에 닿습니다. 웹의 preventDefault() 와 같은 방식입니다.

IME 조합 중의 Enter

IME가 조합하는 동안 렌더러는 Host에 키 이벤트를 아예 보내지 않습니다. 조합 중에 누른 Enter 는 "보내기"가 아니라 "이 음절 확정"이라는 뜻입니다. 이 규칙이 깨지면 한글을 치다 Enter 를 눌렀을 때 조합 중인 음절이 빠진 채 메시지가 전송됩니다. 핸들러는 그런 키를 보지 않으므로 따로 확인할 것이 없습니다.

비제어 TextField

TextField 에는 값 인자가 없습니다. 편집 버퍼, 선택 영역, 조합 상태는 렌더러의 것입니다. Rust는 이벤트로 변화를 압니다. 현재 텍스트를 주는 on_value_change, 제출된 텍스트를 주는 on_submit, 그리고 on_focus_lost 입니다. 값이 필요하면 위의 draft 처럼 상태에 사본을 둡니다. 이 사본은 입력창에서 올라오기만 하고, 아래로 다시 밀어 넣지 않습니다.

이유는 한글입니다. 한글 음절은 치는 동안 자모로 조립됩니다. 조합 중인 텍스트가 Host를 왕복하면, 키를 칠 때마다 텍스트가 렌더러를 떠났다 돌아오면서 조합이 초기화되고 음절이 부서집니다. 일본어와 중국어 입력도 같습니다. 버퍼를 Kotlin에 두면 이 실패는 드문 일이 아니라 일어날 수 없는 일이 됩니다.

text(..) 는 필드가 처음에 가질 텍스트를 줍니다. 처음뿐이어서, 이미 있는 필드에 나중에 다른 값을 주어도 아무것도 바뀌지 않습니다. 다른 문서처럼 다른 텍스트를 보이거나 보낸 뒤 입력창을 비우려면 key 로 필드에 새 정체성을 줍니다. 새 필드는 넘긴 텍스트로 시작합니다.

창 읽기

current_window_size() 는 창의 크기 클래스를 돌려주므로, 화면이 모양을 바꿀 수 있습니다. 휴대폰에서는 한 열, 데스크톱에서는 페이지 옆의 목록입니다. 클래스가 바뀔 때만 다시 구성되므로, 창 가장자리를 끄는 동안 레이아웃 단계마다 Rust 코드가 돌지 않습니다. current_design_system() 은 어떤 디자인 시스템이 그리고 있는지 알려 줍니다.

calculator, notepad, todo, chat 은 모두 이렇게 모양을 바꿉니다. 클래스와 그 너비는 위젯 레퍼런스에 있습니다.

실행 설정

LaunchBuilder 는 첫 프레임 전에 정해지는 것, 곧 테마와 창을 싣습니다. 빌더의 application 이 루트를 실행합니다.

Android, iOS, 브라우저에는 사용자의 main 이 없으므로, 같은 루트를 android_application!, ios_main!, web_application! 으로 등록합니다. 모든 샘플은 진입점들이 함께 쓰는 launch_builder() 하나를 두므로, 플랫폼마다 같은 디자인을 그립니다. 테마는 디자인 시스템이 설명합니다.

애니메이션 계획

애니메이션은 스크롤과 같은 규칙을 따릅니다. 렌더러가 Compose 프레임 시계 위에서 재생하고, 그 사이의 값은 Host에 닿지 않습니다. 작성 API는 렌더러가 재생하는 애니메이션 레코드를 Compose의 이름으로 쓰게 됩니다. 회전, 크기, 이동, 투명도를 받는 graphics_layer, 그리고 목표값이 바뀌면 레코드 하나를 보내는 animate_*_as_state 함수입니다. 둘 다 아직 API에 없습니다(#105). 길이와 곡선을 주지 않은 애니메이션은 디자인 시스템의 MotionRole::Standard 를 따르게 되어, 움직임이 플랫폼을 따릅니다. 위젯 자신의 전환은 지금도 Modifier.motion(role) 을 따릅니다.

상태가 사는 곳

애플리케이션 상태는 Rust에 있는 사용자의 것입니다. UI 로컬 상태는 Kotlin에 있는 렌더러의 것이고, recomposition 런타임은 그것을 Rust로 옮겨 오지 않습니다.
