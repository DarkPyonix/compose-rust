문제 해결

만날 수 있는 실패와 알아보는 법

이 페이지의 문제는 대부분 넷 중 하나입니다. 렌더러가 링커가 기대하는 곳에 없거나, Compose 포크의 아티팩트가 없거나 낡았거나, 툴체인이 엉뚱한 도구를 찾았거나, 건드리면 안 되는 텍스트 경로를 무언가가 건드렸습니다.

빌드가 렌더러를 찾지 못합니다

이 저장소 밖에서는 빌드가 렌더러를 내려받으므로, 여기서의 실패에는 무엇을 시도했고 무엇을 해야 하는지 말하는 메시지가 따라옵니다. 읽어 보십시오. 네트워크가 없는 경우와 릴리스에 대상이 없는 경우를 구별하고, 오프라인이라면 둘 파일과 둘 디렉터리를 알려 줍니다. COMPOSE_RUST_RENDERER_DIR 은 이미 가진 렌더러를 빌드에 알려 줍니다.

체크아웃 안에서는 빌드가 내려받을 수 있는 어떤 것보다 작업 공간의 빌드를 먼저 씁니다. renderer/build/macos(또는 build/linux, build/linux-arm64)의 정적 아카이브가 먼저이고, 그다음이 renderer/build/native-image/dist/lib 의 네이티브 이미지입니다. 네이티브 이미지는 Windows가 빌드하는 것입니다. 정적 아카이브는 실행 파일 안에 링크되므로 시작할 때 찾을 것이 없습니다. 디렉터리가 있는데 비어 있다면 렌더러를 빌드하지 않은 것입니다.

'찾을 것이 없다'는 말의 예외가 Windows의 네이티브 이미지입니다. 그 파일들을 떼어 놓지 마십시오. 네이티브 이미지는 실행 중에 자기 위치를 찾고, Skia와 AWT가 어디 있는지를 자기 디렉터리에서 끌어냅니다. 라이브러리만 따로 다른 곳에 복사하면 로드는 되지만 그것들을 찾지 못합니다.

DXC_MACOS_NATIVE_LIB 와 DXC_LINUX_NATIVE_LIB 는 libcompose_rust_renderer.a 가 있는 디렉터리를 가리키며 다른 어떤 것보다 먼저 확인됩니다. 둘 중 하나가 오래된 디렉터리를 가리키면 방금 빌드한 것이 아니라 그 렌더러가 링크됩니다.

빌드되고 실행되는데 창이 뜨지 않습니다

default-features = false 로 빌드한 바이너리는 이것을 조용히 하지 않습니다. 무엇이 빠졌는지 출력하고 0이 아닌 값으로 끝납니다. mock-renderer 기능으로 빌드한 것은 창 없는 Host를 요청한 것이므로 일부러 조용합니다.

그 밖이라면 렌더러가 출력한 것을 읽습니다. Kotlin/Native 렌더러는 창 줄, 메인 디스패처를 밝히는 장면 줄, 첫 프레임 줄을 출력합니다. smoke-test-kn.sh 는 애플리케이션을 실행하고, 셋이 모두 나오지 않으면 빠진 줄을 밝히며 실패합니다.

창 줄이 없다면 창이 열리지 않은 것이므로 포크의 창 모듈과 고정 커밋을 보십시오(다음 절들). 창은 있는데 프레임이 없다면 장면은 만들어졌지만 그리지 못한 것입니다. Windows에서는 smoke-test-windows.ps1 이 작은 C 호스트를 네이티브 이미지에 링크해 run 을 직접 부릅니다.

빌드가 멈춥니다: 포크의 아티팩트가 없습니다

렌더러는 Compose 포크만 게시하는 모듈에 기대고, 포크는 그것을 ~/.m2 에만 게시합니다. 자기 버전(1.11.1001)으로 낸 패치된 Compose, 0.144.6.1 의 skiko-awt, Linux 타깃, 창 모듈입니다. 렌더러 스크립트는 모두 Kotlin 툴체인을 돌리기 전에 이것을 확인하고, 없으면 이렇게 멈춥니다.

알려 준 명령을 실행하고, 렌더러 스크립트를 다시 실행하십시오. 확인을 먼저 하는 데는 이유가 있습니다. 없는 좌표를 툴체인이 직접 찾으면 그 실패가 캐시되어 고친 뒤에도 남습니다(다음 절).

이 확인은 포크가 게시한 메타데이터도 읽습니다. Gradle은 형제 모듈을 빌드했든 안 했든 포크의 버전으로 적으므로, foundation 1.11.1001 이 어디에도 없는 runtime 1.11.1001 을 요구할 수 있습니다. build-compose.sh 는 실행할 때마다 그런 의존성을 모두 업스트림으로 되돌리고, renderer/scripts/fork-dependencies.sh check 는 남은 것을 나열합니다. 나열되는 것이 있으면 build-compose.sh 를 다시 실행하십시오.

포크를 게시했는데도 의존성 해석이 실패합니다

증상은 ~/.m2 에 파일이 생긴 뒤에도 계속 실패하는 빌드입니다.

원인은 Kotlin 툴체인의 증분 상태입니다. 포크를 게시하기 전에 돈 빌드가 실패한 해석을 renderer/build/incremental.state 에 기록했습니다. 그 항목은 ~/.m2 에 무엇이 있는지가 아니라 좌표와 저장소만으로 키가 정해지므로, 이후의 빌드는 모두 그것을 최신 상태로 보고 그대로 되풀이합니다.

이제는 렌더러 스크립트가 이것을 치웁니다. 포크의 아티팩트가 모두 있으면 require-fork-artifacts.sh 가 포크 버전의 해석 실패를 기록한 상태 파일을 하나씩 지우고 출력합니다: removed a cached resolution failure for a fork version: .... 그 수정 이전의 체크아웃이라면 renderer/build/incremental.state 를 손으로 지우십시오.

렌더러가 빌드되는데 업스트림 Compose로 빌드됩니다

아무것도 실패하지 않는데 포크가 더한 것이 없습니다. 네이티브 텍스트 선택 메뉴가 없거나, 창이 업스트림처럼 동작합니다. 포크의 모듈이 업스트림과 같은 버전으로 게시되어, 툴체인이 캐시해 둔 업스트림이 이긴 것입니다. 그래서 포크는 데스크톱과 macOS의 Compose, skiko-awt를 자기 버전으로 게시합니다. DXC_COMPOSE_EXTENDED_AS 를 설정한다면 업스트림 버전으로 설정하지 마십시오.

Windows: Git Bash와 PATH

build-native-windows.ps1 은 빌드의 bash 부분을 Git Bash에서 돌립니다. Git Bash는 Windows 프로그램이 기대는 것 두 가지를 바꾸고, 그때마다 다른 실패로 나타났습니다.

  • has no extended/window; pin a commit that does: 고정한 커밋에 그 디렉터리가 있는데도 나옵니다. Git Bash는 경로처럼 보이는 인자를 git.exe 가 보기 전에 Windows 경로로 바꾸므로, sparse 패턴 /extended/window/ 가 아무것에도 맞지 않았습니다. 이제 fetch 스크립트는 패턴을 표준 입력으로 git에 넘깁니다.
  • tar (child): Cannot connect to C: resolve failed: 포크의 kotlin.bat 이 툴체인을 풀 때 나옵니다. 배치 파일은 Git Bash의 PATH 를 물려받는데, 거기서는 Git의 /usr/bin 이 System32 보다 앞에 있어서 GNU tar가 돌았고, C:\... 를 원격 호스트로 읽었습니다.
  • Can't find shasum on PATH: 그 뒤로 모든 다운로드의 체크섬이 맞지 않습니다. 툴체인의 런처는 busybox에서 도는데, busybox가 실행할 수 없는 Perl 스크립트인 Git의 shasum 을 찾았습니다.

이제 publish-window.sh 는 System32 를 앞에 두고 Git 자신의 디렉터리를 PATH 에서 뺀 채로 kotlin.bat 을 실행합니다. git 자체를 위한 Git\cmd 만 남깁니다. kotlin.bat 을 직접 실행한다면 Git Bash가 아니라 PowerShell이나 cmd 에서 시작하십시오.

잘못된 JDK: Darwin의 AWT 함정

macOS에서 빌드하는 GraalVM 네이티브 이미지에만 해당합니다. compose-rust는 더 이상 그것을 배포하지 않지만 GraalVM 테스트 경로는 아직 빌드합니다. 좋은 경우는 빌드 스크립트가 no Liberica NIK 25 Full found, and GRAALVM_HOME is not set 으로 멈추는 것입니다. 문제를 대신 잡아 준 것입니다.

나쁜 경우는 PATH 에 업스트림 GraalVM의 native-image 가 있는 것입니다. 빌드는 되지만, 실행하면 AWT 클래스나 심볼이 없다며 실패하거나 창을 아예 열지 않습니다. 업스트림 GraalVM은 Darwin에서 AWT를 빼고 (oracle/graal#13272), Liberica NIK Full은 그것을 정적으로 링크합니다. 실제로 무엇을 가리키는지 확인하십시오.

./scripts/install-nik.sh 가 맞는 것을 설치합니다. 메타데이터 수집과 네이티브 빌드도 같은 JDK를 써야 하며, 스크립트는 GRAALVM_HOME 으로 JAVA_HOME 을 정해 이것을 강제합니다. 그렇지 않으면 도달성 메타데이터가 컴파일하는 것과 다른 JDK를 기술합니다.

앱이 시작하자마자 돌아옵니다

compose_rust_renderer_run 은 프로세스의 메인 스레드에서 불러야 합니다. macOS에서 다른 곳에서 부르면 아무것도 하지 않고 RUN_NOT_MAIN_THREAD(-4)를 돌려줍니다. 네이티브 이미지의 다른 음수 코드도 알아 둘 만합니다.

코드뜻
-1GraalVM isolate를 만들 수 없었습니다.
-2run 을 두 번 불렀습니다.
-3라이브러리가 자기 경로를 알아내지 못해 Skia와 AWT를 찾을 수 없습니다.
-4메인 스레드가 아닙니다.
-5렌더러 스레드를 시작할 수 없었습니다.

Linux의 Kotlin/Native 렌더러도 -2 와 -4 를 같은 뜻으로 씁니다.

IME 문제

서로 다른 실패 셋이 있고, 헷갈리기 쉽습니다.

Enter가 전송하면서 음절을 먹습니다

한글을 치고 음절을 확정하려고 Enter 를 눌렀는데, 그 음절이 빠진 채 메시지가 전송됩니다. 조합 중에 키 이벤트가 Host에 닿은 것입니다. 렌더러는 조합 중에 키 이벤트를 넘기면 안 됩니다. 조합 중의 Enter 는 전송이 아니라 확정이기 때문입니다. 이것을 보았다면 버그는 핸들러가 아니라 렌더러 쪽 키 경로에 있습니다.

치는 동안 조합이 초기화됩니다

음절을 조립하는 동안 글자가 사라지거나 순서가 바뀝니다. 텍스트가 Host를 왕복한 흔적입니다. 조합 중에 무언가가 Rust에서 입력창의 텍스트를 바꾼 것입니다. TextField 가 비제어인 것이 이 때문이고, SetText 는 조합이 끝날 때까지 기다립니다.

네이티브 이미지에서 조합이 아예 되지 않습니다

렌더러를 JVM에서 돌리면 한글 입력이 되는데 네이티브 이미지에서는 되지 않습니다. 이것은 설정 문제로 다룹니다. 미리 컴파일한다고 실행되는 코드가 바뀌지는 않기 때문입니다. InputMethodDescriptor ServiceLoader 리소스, JNI와 리플렉션 메타데이터, 로캘과 문자셋 리소스, CJK 글꼴 대체를 차례로 확인하십시오.

한글을 치면서 메타데이터를 수집하십시오

추적 에이전트는 실제로 실행된 코드 경로만 기록합니다. 앱을 열었다 닫기만 하면 IME에 대해서는 아무것도 기록되지 않습니다. collect-metadata.sh 를 실행하고, 창에 한글을 치고, 이것저것 누른 뒤, 창이 스스로 닫히게 두십시오. 그렇게 하지 않고 수집한 메타데이터로 만든 네이티브 이미지는 텍스트 입력이 정확히 이렇게 망가집니다.

ProtocolError 이벤트

렌더러가 모르는 위젯, 속성, Modifier는 아무것도 충돌시키지 않습니다. 렌더러는 코드와 메시지를 담은 ProtocolError 이벤트를 보냅니다. 이것이 보이면 두 쪽이 스키마에 대해 의견이 다른 것이고, 보통은 실행 중인 Rust 크레이트와 다른 소스로 빌드한 렌더러입니다. 렌더러를 다시 빌드하십시오.

완전한 불일치는 더 일찍 잡힙니다. 빌드가 렌더러의 스키마 해시를 크레이트의 것과 비교하고, 핸드셰이크가 시작할 때 다시 비교해 다르면 초기화를 거부합니다.

테스트가 생성된 Kotlin에서 실패합니다

생성한 Kotlin과 체크인된 파일을 비교하는 테스트가 실패한다면, Rust 스키마를 바꾸고 다시 생성하지 않은 것입니다. 의도한 경보입니다. 스키마가 유일한 원천이고, 갱신되지 않은 Kotlin 쪽은 런타임에 엇나가기보다 빌드에서 실패해야 합니다. cargo run -p compose-rust --bin codegen 을 실행하고 결과를 커밋하십시오.
