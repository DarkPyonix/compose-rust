시작하기

첫 애플리케이션, 그리고 이 저장소 빌드하기

크레이트를 쓰는 데는 Cargo.toml 한 줄이면 됩니다. 필요한 렌더러는 빌드가 내려받기 때문입니다. 이 페이지는 develop 과 이 저장소에서 작업할 때 필요한 렌더러 빌드도 다룹니다.

0.0.2가 주는 것

crates.io의 0.0.2 크레이트에는 작성 API, 경계, 프로토콜, 스키마, Runtime 트레이트, 렌더러 다운로드가 있습니다. 작성 API는 1.0 전의 API라 아직 바뀔 수 있고, 2026-11-14로 계획된 1.0.0부터 안정됩니다(#23, #64). 렌더러는 릴리스와 함께만 게시되므로, develop 을 빌드하려면 같은 체크아웃에서 빌드한 렌더러가 필요합니다. 아래 렌더러 빌드를 보세요.

프로젝트에 더하기

렌더러는 crates.io에 올리기에는 너무 크므로, 릴리스마다 체크섬이 붙은 아티팩트로 실립니다. 받아 오는 일은 빌드 스크립트가 합니다.

cargo build 가 대상에 필요한 렌더러를 알아냅니다. 크레이트의 정확한 버전에 맞는 릴리스 아티팩트를 내려받아 함께 게시된 .sha256 으로 확인하고, target/ 바깥의 캐시에 풀어 링크합니다. 설정할 환경 변수도, 실행할 스크립트도 없습니다. 캐시는 버전과 대상으로 구분되므로 cargo clean 뒤에도 남고 프로젝트끼리 공유됩니다.

macOS(arm64)와 Linux(x64, arm64)에서 렌더러는 Kotlin/Native 정적 아카이브이므로 cargo build 가 내는 프로그램은 실행 파일 하나입니다. 렌더러, Compose, Skia, ICU가 그 안에 있고, 옆에 놓이는 것은 없으며, 불러오는 것은 시스템 자신의 라이브러리뿐입니다. Windows도 Kotlin/Native 렌더러가 들어오면 같아집니다 (#24). 그때까지 Windows는 동반 파일을 옆에 둔 DLL인 GraalVM 네이티브 이미지를 내려받습니다. 0.0.2는 정적 아카이브를 배포하는 첫 릴리스입니다.

변수효과
COMPOSE_RUST_RENDERER_DIR이 디렉터리의 렌더러를 씁니다. 가장 먼저 확인하고, 설정되어 있으면 아무것도 내려받지 않습니다. 직접 빌드한 렌더러, 벤더링한 사본, 오프라인 빌드가 모두 이것으로 됩니다. 빌드 스크립트는 자기 패키지 디렉터리에서 실행되므로 경로는 절대 경로여야 합니다.
COMPOSE_RUST_CACHE_DIR캐시 위치를 $HOME/.cache/compose-rust(Windows는 %LOCALAPPDATA%\compose-rust)에서 옮깁니다.

네트워크 없이 빌드하면 어떤 파일을 어디에 둘지 알려 줍니다. 거기에 두기만 하면 됩니다.

렌더러 없이 빌드하기

default-features = false 로 빌드하면 렌더러 없이 빌드되며, 헤드리스나 문서용 빌드에 씁니다. 그렇게 빌드한 바이너리는 무엇이 빠졌는지 알리고 0이 아닌 값으로 끝납니다. 창 없이 0 을 돌려주지 않는 것은, 아무것도 그리지 않은 프로그램과 일을 마친 프로그램을 구별할 수 있어야 하기 때문입니다. mock-renderer 기능은 일부러 렌더러 없이 경계를 구동하며, 테스트와 스스로 그리는 무언가에 Host를 넣을 때 씁니다.

첫 애플리케이션

compose-rust 애플리케이션은 main 이 컴포저블 하나를 실행하는 Rust 프로그램입니다. 아래는 그 자체로 완전한 프로그램입니다. 각 줄은 UI 작성하기가 설명합니다.

compose-rust = "0.0.2" 로는 이 프로그램이 그대로 빌드됩니다. cargo run 이 렌더러를 내려받고 창을 엽니다.

0.0.2 이후 develop 에 있는 것을 쓰려면 체크아웃 안에서 돌립니다. 체크아웃에서는 빌드가 내려받을 수 있는 어떤 것보다 직접 빌드한 렌더러를 먼저 링크하고, develop 의 스키마로 빌드한 렌더러를 싣는 릴리스는 없습니다. 렌더러를 한 번 빌드한 다음(아래), 샘플을 실행합니다.

체크아웃 밖의 자기 프로젝트는 크레이트를 경로로 의존하고, 직접 빌드한 렌더러를 COMPOSE_RUST_RENDERER_DIR 로 가리킵니다. 빌드는 다른 스키마로 빌드된 렌더러를 거부하기 때문입니다.

샘플

samples/ 에는 실제 애플리케이션을 본뜬 애플리케이션 열한 개가 모두 작성 API로 쓰여 있고, 그 화면을 스크린숏 테스트용으로 기록하는 frames 가 함께 있습니다. 샘플은 베껴 쓰라고 있는 것입니다. 샘플 하나는 한 줄짜리 main.rs 를 앞에 둔 라이브러리라서, 같은 화면이 Android, iOS, 브라우저에서도 돕니다. 적응형 샘플 넷은 플랫폼이 고르는 디자인 시스템을 따릅니다. 통일형 일곱은 각자 디자인 시스템 하나, Cupertino를 정하고 어디서나 같게 그립니다.

샘플다루는 것함께 읽을 곳
calculator빽빽한 버튼 격자, Row 와 Column 중첩, 메모리 레지스터, 키 옆이나 시트에 놓이는 계산 기록상태, 창 읽기
notepad여러 줄 편집, IME, 워커 스레드의 파일 I/O, 목록이 페이지 옆이나 시트에 놓이는 여러 문서TextField, 워커 스레드

DXC_DESIGN 과 DXC_SCHEME 은 샘플의 디자인 시스템과 색 구성을 덮어씁니다. 그래서 어떤 샘플이든 일곱 시스템 중 어느 것으로든, 밝게든 어둡게든 볼 수 있습니다.

이 저장소에서 작업하기

아래는 compose-rust 자체를 고칠 때의 이야기이고, 렌더러 툴체인도 필요합니다. 설정 점검부터 합니다. 빌드에 필요한 도구를 모두 확인하고, 빠진 것을 말하고, 고치는 명령을 출력합니다.

워크스페이스는 Rust 1.85+(edition 2024)를 대상으로 하며, rustfmt 와 clippy 가 필요합니다. Kotlin은 따로 설치할 것이 없습니다. renderer/kotlin(Windows는 kotlin.bat)이 처음 쓸 때 고정된 툴체인을 내려받습니다. ./scripts/check.sh --no-kotlin 은 Kotlin 검사를 건너뛰고, --full 은 벤치마크를 전체 표본으로 돌립니다.

렌더러 빌드

렌더러는 Compose 포크 thisisthepy/compose-multiplatform-core-extended 의 고정된 커밋 위에서 빌드합니다. 포크는 게시된 Compose에 없는 것, 곧 Linux 타깃, 텍스트 선택 메뉴, 복사 키를 더합니다. 데스크톱 창 코드도 포크의 것입니다. 모든 OS의 창, 입력, IME, 메뉴, 크롬, 크기 조절이 그렇습니다. 이 저장소에는 렌더러가 그 창에 붙는 접착 코드만 남습니다.

순서가 중요합니다. 먼저 포크를 ~/.m2 에 게시하고, 그다음 렌더러를 빌드합니다. 렌더러 스크립트는 Kotlin 툴체인이 돌기 전에 포크의 아티팩트를 확인하고, 하나라도 없으면 실행할 명령을 알리고 멈춥니다.

렌더러 스크립트는 저마다 같은 고정 커밋에서 포크의 창 모듈을 게시하고 (renderer/scripts/publish-window.sh), 그다음 Compose, Skia, 인터프리터가 들어간 정적 라이브러리 하나, libcompose_rust_renderer.a 를 만듭니다. Rust 빌드가 자기 스키마와 대조하는 schema-hash.txt 도 함께 둡니다. 체크아웃에서 Rust 빌드는 내려받을 수 있는 어떤 것보다 이 아카이브를 먼저 링크합니다. DXC_MACOS_NATIVE_LIB 와 DXC_LINUX_NATIVE_LIB 는 정적 렌더러 디렉터리를 직접 가리키며, 다른 모든 것보다 먼저 확인됩니다.

Windows는 Kotlin/Native 렌더러가 들어올 때까지 renderer/desktop/scripts/build-native-windows.ps1 로 GraalVM 네이티브 이미지를 빌드합니다(#24). 이 스크립트는 bash로 된 부분을 Git Bash에서 돌립니다. Git Bash의 PATH 가 그 부분에 무엇을 하는지는 문제 해결에 있습니다.

Compose와 Skia를 미리 컴파일하므로 첫 빌드는 느립니다. Kotlin 쪽이나 포크 고정 커밋이 바뀔 때만 다시 하면 되고, 평소의 Rust 작업은 만들어 둔 라이브러리를 그대로 씁니다.

애플리케이션 스모크 테스트

renderer/desktop/scripts/smoke-test-kn.sh 는 정적 렌더러에 링크된 실행 파일을 돌리고, 창이 뜨지 않으면 실패합니다. 실행이 0 으로 끝나고, 창 줄, 플랫폼의 메인 디스패처 위의 장면 줄, 첫 프레임 줄을 출력해야 합니다.

JVM 개발 셸

렌더러 자체를 고칠 때는 개발 셸이 가장 빠른 루프이며, 핫 리로드와 @Preview 가 됩니다. JVM은 여기서만 허용되고, 배포물에는 들어가지 않습니다.

생성 코드 검사

테스트 하나가 체크인된 Kotlin 프로토콜 파일과 Rust 스키마가 생성하는 내용을 비교합니다. 스키마를 바꾸고 다시 생성하지 않으면 이 테스트가 실패합니다. 의도한 경보입니다. 스키마가 유일한 원천이고, 갱신되지 않은 Kotlin 쪽은 런타임에 엇나가기보다 빌드에서 실패해야 합니다. codegen 바이너리로 다시 생성합니다.
