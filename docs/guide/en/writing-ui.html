Writing UI

Composables, state and events

compose-rust's authoring API follows Compose. A composable is a function, a widget is a call with Compose's name, state lives in remember, and when state changes only the code that read it runs again. Nothing compares trees to find what changed.

Where the API is

The API is on develop and is released with compose-rust 1.0.0 on 2026-11-14 (#23, #64). The 0.0.1 crate on crates.io does not contain it. Until 1.0.0 you use it from a checkout of this repository, as Getting started shows. Names can still change before the release.

A composable is a function

Mark a function with #[composable] and call widgets inside it. Two glob imports bring in everything: compose_rust::runtime for state and effects, and compose_rust::ui for the widgets and Modifier.

#[composable] does what the Compose compiler plugin does to a @Composable function. It gives the call a group, gives every branch of an if and a match a group of its own, and makes the function skippable and restartable. You never write groups by hand. They close correctly through continue, break, return, ? and unwinding, because the macro owns them rather than you.

launch runs the composable as the application with every choice left to its default. application is the same function under Compose Desktop's name. Launch choices below shows how to name a theme and a window.

A widget is a statement

Text("Hello") creates a description of a widget. The end of the statement hands it to the composition. The methods in between set what Compose takes as named arguments: Text(title).type_role(TypeRole::Title).max_lines(1) is Compose's Text(title, style = ..., maxLines = 1).

  • What a widget cannot do without is the argument. A Text takes its text, a Button its label, a Slider its value and a Dialog whether it is open. Everything else is a method.
  • Children are a closure. A container composes its children when you call content, and the closure runs at once: Row().content(|| { ... }).
  • Every widget takes a Modifier. Start a chain from the value Modifier, as Compose does: Modifier.fill_max_width().padding_role(SpaceRole::Md). The order of the calls does not matter, because each kind of modifier has a fixed place in the node's chain.
  • Do not bind a widget to a variable. A widget bound with let is composed when the variable goes out of scope, which puts it in the wrong place among its siblings.

The widget vocabulary is the one in the schema, listed in the widget reference. The authoring API defines no widget or property of its own, so what you can write and what the renderer can draw are the same list. The minimal sample is a playground with every control the schema has.

Your own composables

Split a screen into functions the way you would in Compose. Parameters are ordinary Rust parameters, and a closure parameter is how a composable takes content of its own.

A call whose parameters equal last time's is skipped. Inside a scope that runs again, task_row with the same title and the same state does not run its body, and its nodes stay as they were. The macro decides what it can compare from each parameter's type. A parameter that is not Clone and PartialEq, a borrow, a generic or an impl Trait cannot be compared, so a function that takes one is run by its caller every time instead of being skipped.

State and recomposition

mutable_state_of(value) makes a MutableState. It records which scopes read it. Writing it marks exactly those scopes invalid, and the next frame runs them again. That is the whole change detection.

CallWhat it does
state.get()Reads the value and subscribes the current scope to it.
state.with(|value| ...)Reads by reference, for a value too large to clone, such as a list.
state.get_untracked()Reads without subscribing. Use it in a handler, which is not a scope.
state.set(value)Writes. A value equal to the current one changes nothing.
state.update(|value| ...)Changes the value in place.
derived_state_of(|| ...)A value computed from other states. Its readers run again only when the result changes.
  • A state is a handle. Cloning it gives a second handle to the same value, which is how a move closure takes it: clone first, then move the clone.
  • Equal writes are free. The default policy compares with PartialEq. mutable_state_of_with_policy(value, never_equal_policy()) treats every write as a change, for a value that is expensive to compare, such as a long list you change in place.
  • Writes in one frame coalesce. Several writes before the next frame cause one recomposition, not one each.
  • One changed text sends one record. Changing one Text sends a single property record. Its siblings and its parent do not run.

The calculator sample keeps a display, a memory register and a tape in states. The todo sample keeps a five thousand row list in one state with never_equal_policy.

Positional memory and keys

remember(|| ...) runs its closure the first time a call site composes and hands back the same value every time after. The value belongs to the call site: the path of groups and the order of calls inside them. When a branch stops being taken, what it remembered goes with it. When a loop gets shorter, the iterations it lost drop theirs. remember_with_key(key, || ...) computes the value again when the key changes.

In a loop, position is sometimes the wrong identity. When items can move, wrap each one in key. A keyed item that changes place is sent as a move rather than a removal and a re-creation, and its remembered values travel with it.

Lazy lists take keys the same way, through items_keyed. See Lists & streaming.

Effects

Composing describes the screen and does nothing else, because the runtime may run a scope, skip it or run it again. Work that belongs to a place in the composition goes in an effect. Effects run after the composition is applied, on the UI thread, inside the same Host call.

FunctionCompose nameWhen it runs
side_effect(|| ...)SideEffectAfter every applied composition of its scope.
launched_effect(key, || async { ... })LaunchedEffectA future started when the call site enters, restarted when the key changes, cancelled when it leaves.
disposable_effect(key, || { ...; on_dispose(|| ...) })DisposableEffectRuns when the call site enters or the key changes. The cleanup runs before the next run and when it leaves.
remember_coroutine_scope()rememberCoroutineScopeA scope to start futures from a handler. They are cancelled when the call site leaves.

A future is polled on the UI thread by a small executor the runtime owns. Waiting costs nothing, and whatever wakes the future asks for a frame. delay waits for a duration and with_frame_nanos waits for the next frame. A state written during a recomposition is deferred to the next frame, so a composition never feeds itself.

Work on worker threads

Handlers, composition and effects all run on the UI thread, so anything that blocks belongs somewhere else: a PTY read, a network call, file I/O. There are two ways out.

  • with_worker(|| ...) runs a closure on a worker thread and resumes the future with its result on the UI thread. It is Compose's withContext(Dispatchers.IO): let text = with_worker(move || std::fs::read_to_string(path)).await;
  • A thread of your own writes a state. MutableState is Send. A worker that writes one queues the change and asks for a frame, and the UI thread recomposes exactly the scopes that read it.

Either way your code never calls a boundary function, and there is no queue between the two sides to fill up. The chat sample streams a reply from its own thread a few characters at a time. The notepad and todo samples read and save files off the UI thread.

Event handlers

Handlers are ordinary Rust closures, given with methods such as on_click, on_change and on_submit. A handler has to be 'static, so it owns what it uses: clone a state, then move the clone in.

Handlers run synchronously. The renderer calls into the Host on its UI thread, your handler runs, the runtime recomposes, and the batch of changes travels back in the same call. Nothing is queued. Because the handler holds the UI thread, it must stay cheap, and the work it starts goes to a worker as above.

Consuming a key: Enter versus Shift+Enter

A chat input needs Enter to send and Shift+Enter to insert a newline. A multiline TextField with an on_submit handler does exactly that: Enter submits the text and Shift+Enter is a newline.

To decide for yourself, on_key_down sees the key with its modifier keys. Today the schema carries one key, Key::Enter. Calling consume() on the event keeps the field from acting on it. The answer reaches the renderer as the return value of the same call, the way preventDefault() does on the web.

Enter during IME composition

While an IME is composing, the renderer sends no key events to the Host at all. An Enter pressed mid-composition means "commit this syllable", not "submit". If that rule were broken, pressing Enter while typing Korean would submit the message with the composing syllable missing. Your handler never sees those keystrokes, so it needs no check of its own.

The uncontrolled TextField

TextField has no value argument. The edit buffer, the selection and the composition state belong to the renderer. Rust learns about changes through events: on_value_change with the current text, on_submit with the submitted text, and on_focus_lost. Keep a copy in a state if you need it, as the draft above does. That copy goes up from the field and is never pushed back down.

The reason is Hangul. A Korean syllable is assembled from jamo as you type. If in-progress text made a round trip through the Host, every keystroke would leave the renderer, come back, and reset the composition, destroying the syllable. Japanese and Chinese input behave the same way. Keeping the buffer in Kotlin makes that failure impossible rather than rare.

text(..) gives the field the text it starts with, and only that: a later value changes nothing on a field that already exists. To show other text, such as another document, or to clear an input after sending, give the field a new identity with key. The new field starts with the text you pass.

Reading the window

current_window_size() returns the window's size class, so a screen can change shape: one column on a phone, a list beside the page on a desktop. Only a class change recomposes, so dragging a window edge does not run Rust code on every layout pass. current_design_system() says which design system is drawing.

calculator, notepad, todo and chat each change shape this way. The widget reference lists the classes and their widths.

Launch choices

LaunchBuilder carries what is settled before the first frame: the theme and the window. application on the builder runs the root.

Android, iOS and the browser have no main of yours, so the same root is registered with android_application!, ios_main! and web_application!. Every sample keeps one launch_builder() that all entry points share, so each platform draws the same design. Design systems explains the theme.

Animation Planned

Animation follows the same rule as scrolling: the renderer plays it on the Compose frame clock, and the values in between never reach the Host. The authoring API will write the animation records the renderer plays, with Compose's names: graphics_layer for rotation, scale, translation and alpha, and the animate_*_as_state functions, which send one record when the target changes. Neither is in the API yet (#105). Without an explicit duration and curve an animation will take the design system's MotionRole::Standard, so motion follows the platform. A widget's own transitions already follow Modifier.motion(role).

Where state lives

Application state is yours, in Rust. UI-local state is the renderer's, in Kotlin, and the recomposition runtime does not move it into Rust.

StateOwnerWhy
Application and domain stateRustIt is your program.
Text being edited, IME compositionKotlinComposition must never make a round trip (see above).
Scroll positionKotlinIt would be a frame behind if Rust owned it.
FocusKotlinThe platform already owns focus.
Animation progressKotlinIt runs on the Compose frame clock.
Whether a dialog, menu, dropdown or sheet is openKotlinThe value you pass seeds it, and the renderer owns the enter and the exit, so the animation never makes a round trip.
The position a slider drag is passing throughKotlinFollowing a finger should not cost a boundary call.
The app zoom levelKotlinIt is saved per application by the renderer. See Architecture.
