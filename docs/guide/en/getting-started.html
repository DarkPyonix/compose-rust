Getting started

Your first application, and building this repository

Using the crate is one line in a Cargo.toml, because the build downloads the renderer it needs. This page also covers building the renderer, which work on develop and on this repository needs.

What 0.0.2 gives you

The 0.0.2 crate on crates.io contains the authoring API, the boundary, the protocol, the schema, the Runtime trait and the renderer download. It is a pre-1.0 API that may still change, and it is stable from 1.0.0, planned for 2026-11-14 (#23, #64). A renderer is published only with a release, so a build of develop needs a renderer built from the same checkout: Build the renderer below.

Adding it to a project

The renderer is far too large for crates.io, so each release carries it as a checksummed artifact. Fetching it is the build script's job, not yours.

cargo build works out which renderer the target needs. It downloads the release artifact for the crate's exact version, checks it against the published .sha256, unpacks it into a cache outside target/, and links it. There is no environment variable to set and no script to run. The cache is keyed by version and target, so it survives cargo clean and is shared between projects.

On macOS (arm64) and Linux (x64 and arm64) the renderer is a Kotlin/Native static archive, so the program cargo build produces is one executable. The renderer, Compose, Skia and ICU are inside it, nothing sits beside it, and it loads only the system's own libraries. Windows gets the same once its Kotlin/Native static archive is published (#24). Until then Windows downloads a GraalVM native image, a DLL with its companions beside it. 0.0.2 is the first release that ships the static archives.

VariableEffect
COMPOSE_RUST_RENDERER_DIRUse the renderer in this directory. It is checked first, and nothing is downloaded when it is set. A renderer you built yourself, a vendored copy and an offline build all work through it. The path must be absolute, because a build script runs in its package's directory.
COMPOSE_RUST_CACHE_DIRMoves the cache off $HOME/.cache/compose-rust (%LOCALAPPDATA%\compose-rust on Windows).

A build with no network says which files to put where. Putting them there is all it takes.

Building without a renderer

default-features = false builds with no renderer at all, for a headless or documentation build. A binary built that way says what is missing and exits non-zero. It does not open no window and return 0, because a program that drew nothing has to be distinguishable from one that finished its work. The mock-renderer feature drives the boundary with no renderer on purpose, for tests and for embedding the Host in something that draws for itself.

Your first application

A compose-rust application is a Rust program whose main launches a composable. This one is a complete program. Writing UI explains each line.

With compose-rust = "0.0.4" this program builds as it is. cargo run downloads the renderer and opens the window.

To use what is on develop after 0.0.2, run it inside a checkout. There the build links the renderer you built before anything it could download, and no release carries a renderer built from develop's schema. Build the renderer once (below), then run a sample:

A project of your own outside the checkout depends on the crate by path and names the renderer you built with COMPOSE_RUST_RENDERER_DIR, because the build refuses a renderer built from a different schema.

Samples

The samples/ directory holds eleven applications, each a clone of a real one and each written on the authoring API, plus frames, which records their screens for the screenshot tests. They exist to be copied: a sample is a library with a one line main.rs in front of it, so the same screen also runs on Android, iOS and in a browser. The four adaptive samples take whichever design system the platform picks. The seven unified ones each name one design system, Cupertino, and draw the same way everywhere.

Working on this repository

Everything below is for working on compose-rust itself, which needs the renderer toolchain as well. Start with the setup check. It checks every tool the build needs, names what is missing, and prints the command that fixes it.

The workspace targets Rust 1.85+ (edition 2024), and rustfmt and clippy are required. Kotlin needs nothing installed: renderer/kotlin (kotlin.bat on Windows) downloads the pinned toolchain on first use. ./scripts/check.sh --no-kotlin skips the Kotlin gate, and --full runs the full benchmark sample.

Build the renderer

The renderer is built on a pinned commit of thisisthepy/compose-multiplatform-core-extended, a Compose fork. The fork adds what the published Compose lacks: the Linux targets, the text selection menu and the copy keys. It also owns the desktop window code: the window, input, IME, menus, chrome and resize for every OS. This repository keeps only the renderer's glue to that window.

The order matters. Publish the fork into ~/.m2 first, then build the renderer. The renderer scripts check for the fork's artifacts before the Kotlin toolchain runs and stop with the command to run if any is missing.

Each renderer script publishes the fork's window modules at the same pinned commit (renderer/scripts/publish-window.sh) and then produces one static library, libcompose_rust_renderer.a, with Compose, Skia and the interpreter inside it, and a schema-hash.txt that the Rust build checks against its own schema. In a checkout the Rust build links that archive before anything it could download. DXC_MACOS_NATIVE_LIB and DXC_LINUX_NATIVE_LIB name a static renderer directory directly, ahead of everything else.

On Windows, renderer/desktop/scripts/build-windows.sh builds the Kotlin/Native renderer, and DXC_WINDOWS_NATIVE_LIB pointing at its output (renderer/build/windows) makes the build link it: one executable, linked by MSVC, with nothing beside it. Without that variable Windows uses the GraalVM native image, built with renderer/desktop/scripts/build-native-windows.ps1, until the Kotlin/Native archive is published (#24). Both scripts run their bash parts under Git Bash. Troubleshooting covers what Git Bash's PATH does to them.

The first build is slow, because Compose and Skia are compiled ahead of time. You repeat it only when the Kotlin side or the fork pin changes; ordinary Rust work reuses the library.

Smoke-test an application

renderer/desktop/scripts/smoke-test-kn.sh runs an executable linked against the static renderer and fails unless the window came up: the run exits 0 and prints the window line, the scene line on the platform's main dispatcher and the first frame.

The JVM development shell

The development shell is the fastest loop when you work on the renderer itself, with hot reload and @Preview. The JVM is allowed only here. Shipped artifacts never contain one.

The generated code check

One test compares the checked-in Kotlin protocol file against what the Rust schema generates. If you change the schema and forget to regenerate, that test fails. That is the intended alarm: the schema is the single source, and a Kotlin side that was not updated should fail the build rather than misbehave at runtime. Regenerate with the codegen binary.
