# Submitting to Flathub

Everything Flathub reviews is generated by `tools/packager-linux/flatpak.sh`. The
`Linux packaging` workflow generates it for the calculator sample under the placeholder ID
`dev.darkpyonix.PlaceholderAppId` and uploads it as the `flathub-submission-placeholder`
artifact. It also lints the result with Flathub's own linter, and builds and starts the same
manifest under the sample's real ID.

What is still open is the application ID. Once the owner has chosen it, the submission is the
same command with that ID.

## 1. Before the pull request (owner)

- [ ] Choose the application and its ID. Flathub does not accept tech demos, so a sample
      goes in only if it is meant to be used.
- [ ] Prove control of the ID's domain. `dev.darkpyonix.*` means `darkpyonix.dev`. After the
      app is accepted, verify it on flathub.org (Developer settings, Verification), which asks
      for a token at `https://darkpyonix.dev/.well-known/org.flathub.VerifiedApps.txt`.
      An `io.github.<user>.*` ID is verified through the GitHub account instead.
- [ ] Publish the release the manifest points at. Each architecture needs one archive, with
      the executable and the renderer at its top level, and the SHA-256 of each.
- [ ] Give the listing at least one screenshot: `[linux.store] screenshots` in an overlay,
      as a stable URL (a release asset or a file in the repository at a tag). Flathub's
      linter refuses a listing without one.
- [ ] Decide the release notes for this version (`[linux.store] release_notes`).

## 2. Generate the submission

```sh
cargo build --release -p packager-linux
PACKAGER_LINUX=target/release/packager-linux tools/packager-linux/flatpak.sh \
    --dioxus-toml samples/calculator/Dioxus.toml \
    --overlay tools/packager-linux/samples.toml --overlay store.toml \
    --app-id <THE.CHOSEN.ID> \
    --exec sample-calculator \
    --icon samples/calculator/assets/icon.png --icon samples/calculator/assets/icon-256.png \
    --version <version> \
    --prebuilt-url <x86_64 archive URL> --prebuilt-sha256 <hex> --prebuilt-arch x86_64 \
    --prebuilt-url <aarch64 archive URL> --prebuilt-sha256 <hex> --prebuilt-arch aarch64 \
    --out flathub/ --build repo/ --lint
```

`store.toml` holds what is specific to this submission (screenshots and release notes). For an
application built from source, pass `--source-url`, `--source-sha256` and `--cargo-lock`
instead of the prebuilt archives, and `--renderer-url`, `--renderer-sha256` and
`--renderer-arch` for each architecture's renderer.

`flathub/` then holds `<ID>.json`, `<ID>.desktop`, `<ID>.metainfo.xml`, the icons under
`icons/`, and `cargo-sources.json` for a build from source. These are the files of the
`flathub/<ID>` repository.

## 3. Check before opening the pull request

- [ ] `lint-manifest.json` and `lint-repo.json` in `flathub/` show no errors other than the
      ones only Flathub can clear (the ID's domain not verified yet).
- [ ] `flatpak run <ID>` opens the window. Under a virtual display, the workflow's
      calculator step shows how.
- [ ] `appstreamcli validate --no-net flathub/<ID>.metainfo.xml` passes.
- [ ] The runtime branch (`[linux.store] flatpak_runtime_version`, default 26.08) is the
      newest one Flathub offers.

## 4. Pull request

Fork `flathub/flathub`, branch from `new-pr`, add the files from `flathub/` at the
repository root, and open the pull request against `new-pr` titled `Add <ID>`. A reviewer
answers there. Once it is merged, Flathub creates `flathub/<ID>` and the owner is given
write access. Every later release is a commit there that changes the archive URLs and digests.
